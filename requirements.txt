# Runtime dependencies for the Vercel Python Functions under /api. Separate
# from ml/requirements.txt, which pins CUDA training-time packages (cupy,
# duckdb) that don't belong in a serverless inference bundle.
#
# xgboost-cpu is the CPU-only PyPI distribution (same `xgboost` import) —
# the regular `xgboost` wheel pulls in nvidia-nccl-cu13 as a hard dependency
# (~290 MB) purely for optional multi-GPU support this serverless function
# never uses.
#
# Pinned exactly to 3.4.1, the version the promoted crowd model was trained
# with (see ml/crowd/models/all-history-v1/metadata.json's xgboost_version).
# xgboost-cpu 3.1+ only publishes `manylinux_2_28` wheels, no `manylinux2014`
# variant, so this still gets force-built from source on Vercel ("Force-
# bundling ... without compatible wheels") — but Vercel's per-function
# package size limit is now 5 GB (previously ~250 MB), so the from-source
# build's ~300 MB output no longer blows the limit the way it used to.
#
# This pin was previously held down to 3.0.5 (the newest manylinux2014
# wheel) specifically to dodge that from-source build. That silently
# introduced a real bug: xgboost 3.0.5's DMatrix construction disagreed with
# 3.4.1 on how this model's native-categorical columns route through the
# trees, so every live crowd-inference prediction came back ~1000x too low
# regardless of sensor or location (e.g. Bourke Street Mall: 1.07/hr instead
# of ~1000/hr) — silent because the endpoint still returned a plausible-
# looking "degraded" quality status with a real number, just a wrong one.
# Confirmed by loading the same features under both versions locally. Any
# future version bump here MUST match the training xgboost_version exactly,
# not just "same major version" — verify with a real prediction, not just
# that the model loads without error.
xgboost-cpu==3.4.1
numpy>=1.26,<1.27
scipy>=1.13,<1.14
